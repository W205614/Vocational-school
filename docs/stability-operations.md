# 稳定性修复与本机运维

默认本机部署使用模拟支付、短信和本地视频，不接入真实渠道，不承诺生产容量、跨主机容灾或多节点高可用。独立商业部署包已有账户、云媒资与安全约束实现，仍需目标云环境及供应商验收，详见[商业化运行手册](commercial-ha.md)。

## 业务变化

- 分类禁用与关联已上架课程的下架在同一事务内完成，任一失败回滚。订单事务中的购物车清理失败直接传播，订单、明细和本地结算事件一起回滚。
- MFA 设置仅对明确的凭据及权限拒绝累计失败；身份服务不可用不计为凭据失败。登录始终调用必需的 MFA 组件，由组件按配置判断是否需要验证。
- 网关仅从明确配置的 Nginx 地址接受单跳客户端地址和协议；不信任直连请求的转发头。DNS 更新失败时取消旧信任，本地 HTTP 刷新 Cookie 仍可用，正式安全配置可通过 `tj.auth.cookie.require-secure=true` 强制 Secure。
- 优惠全额抵扣后按 `PAYED/ZERO` 成交，不创建支付流水；通过原 `order.pay` 事件确认优惠券和学习权益。零金额退款沿用申请／审批，本地完成退款和撤权，不请求渠道退款。
- 支付核对校验渠道单号、实际金额与成功时间。持久任务每批最多 100 单，失败退避，核对过期／关闭支付单，七天后转待人工处理。关闭业务订单发现已付仍记录冲突，不自动恢复订单或退款。
- 管理端「可靠性与补偿」可查看渠道异常、记录处理依据和重试 DEAD 核对任务。操作校验管理员权限和版本；标记处理不会删除资金事实，也不会伪造支付成功。
- 考试结算采用每页 1000 条、固定序列上界的内部扫描，不再因超过 10000 条记录永久阻塞。必须同时升级考试和学习模块；混合新旧协议会阻塞结算。
- 积分采用月份共享锁，冻结采用排他锁；结算事务不调用用户服务。排名冻结后昵称暂显示「同学」，异步首次成功补齐后固定；历史昵称不改写。冻结后的迟到积分继续进入对账，不能宣称自动补发赛季奖励。
- 榜单以匹配索引分页并分别查询本人排名、前一名和总数，不重复执行全月窗口排序。实际容量仍取决于资源、数据规模和业务负载。
- 环境接口按实际配置返回本地或云上传／播放能力。默认本机使用本地媒体；独立 `CLOUD_COS` 模式已有私有上传、扫描转码与逐请求权益校验实现，真实 COS、原生处理和吞吐仍待供应商环境验收。真实模式不会自动退回模拟成功。

## 升级已有部署

不要重新执行 `setup.py prepare` 或首次初始化，不要覆盖既有 `.env`、密钥及数据卷。

当前备份按用户决定继续停用，也没有有效本地恢复集。下面是工具在具备有效完整备份后的升级流程；本轮只修改源码、在隔离环境验证并核对 CI，不执行日常部署升级。`upgrade_existing.py deploy` 会拒绝缺失或无效的完整备份；不要为了发布本轮改动重新启用备份或绕过这个保护。将来如需实际升级，应先另行确定数据保护和发布方式。

公共 `deploy/compact/compose.yaml` 不再保存本机镜像 SHA、搜索卷和 RabbitMQ 主机名。旧版本更新源码前，先按[部署手册](../deploy/compact/README.md#干净启动)的独立复制命令保存原生效文件；旧版本尚无 `migrate-runtime` 命令，不能先拉取新模板再拿它替代原配置。若存在未完成的 `ops-status/resume.json`，先用原版本恢复备份状态，再升级。已经迁移的部署直接使用私有 `.local/compose.runtime.yaml`；所有 Compose 命令必须指定部署目录作为 `--project-directory`，不要直接运行公共模板替换已有容器。

1. 仅在已明确重新启用备份后，保存当前未提交改动，运行 `python deploy/compact/backup.py` 完成本项目完整备份与校验。完成后读取 `deploy/compact/.local/ops-status/backup.json` 的 `lastBundle` 字段，作为后续 `--backup` 参数；当前停用状态不执行此步。
2. 提交本次生产源码，运行 `python deploy/compact/setup.py build` 重建全部七个应用／网页镜像。
3. 运行 `python deploy/compact/upgrade_existing.py stage`，取得已验证候选目录。候选包含源码与七镜像绑定，不修改现有运行部署。
4. 在独立副本验证新迁移及受影响链路，保留原数据与媒体；随后用以下入口停写、增量迁移、更新配置和镜像：

```powershell
python deploy/compact/upgrade_existing.py deploy --candidate <本项目.local/candidates/提交目录> --backup <本项目.local/backup/完整备份目录>
```

发布与备份竞争同一进程锁。增量配置工具保留原镜像引用、存储路径、数据库密码及自定义代理配置，原配置存于本机 `.local/operations-upgrade/`。仅新增数据库迁移，不改写已执行的校验和迁移。

若此次更新包含监控规则，复用中的 Prometheus 不会自动重载挂载文件。日常项目执行 `docker kill --signal HUP tianji-compact-prometheus-1` 后，检查 `http://127.0.0.1:24590/api/v1/rules` 是否出现 `BusinessOperationBacklog`、`ReliabilityMetricsStale`，并核对 `/api/v1/targets` 全部在线；其他项目必须改用实际容器名和端口。此信号只要求重载配置，不删除容器或数据。不能仅凭文件已复制认定告警已生效。

失败时保留数据、事件和诊断材料，不自动用旧 SQL 覆盖新增订单／评分／支付事实。需要回退时先停写并确认旧代码与当前表结构兼容；不兼容则在副本核对增量后制定数据回迁，不能删除新表或丢弃新事实。

## 备份状态、空间与计划任务

本机计划任务当前禁用，状态为 `DISABLED_BY_USER`，没有保留有效本地恢复集。下面的备份命令和保留策略仅说明明确重新启用后的工具行为，不代表当前已有备份。

手动完整备份：`python deploy/compact/backup.py`。`--online` 仅是部分在线导出，不计入完整备份成功记录。默认完整备份短暂停止原本运行的业务和网页，捕获 MySQL、Redis、RabbitMQ、配置、签名密钥及真实媒体字节，校验后恢复原状态。

Windows 注册：`powershell -NoProfile -File deploy/compact/register_backup_task.ps1`，任务名 `Tianji-Backup-tianji-compact`。再次注册更新同一个任务，不创建重复任务；采用当前登录用户的有限权限，不保存账户密码。主机时区要求北京时间。Python 安装目录须包含 `pythonw.exe`；任务通过它无窗口启动，备份工作进程及其命令使用隐藏控制台，避免每次检查弹出终端。停用可在 Windows 任务计划程序禁用该任务。

- 每日 03:30 到期，每 15 分钟检查一次欠缺备份；成功后当日跳过。03:30 是计划时间，电脑、当前用户会话或 Docker 不可用时无法保证准点执行，条件恢复后补执行。检查进程会退出，不保留常驻 Python 进程。
- Docker Desktop 关闭：记录 `SKIPPED_DOCKER_UNAVAILABLE`，不启动 Docker Desktop，也不追加失败日志。
- Docker 可用但原容器停止：仅临时启动已初始化的 MySQL、Redis、RabbitMQ，完成后停止它们；不启动业务和网页，也不启动 ES。
- 容器暂停或正在重启：跳过，不改变其状态。维护恢复 journal 仅属于当前部署，不导入恢复副本。
- 实际备份失败：保留不完整材料并暂停自动大备份，避免每次检查重复产生全量失败包；排查后执行 `python deploy/compact/maintenance.py retry` 显式重试。
- 状态存于 `.local/ops-status/`，覆盖更新。`scheduler.json` 记录最近检查时间与退出码，`backup.json` 的 `lastSuccess` 才是完整备份成功时间；计划任务的“下次运行时间”包含补执行检查。错误日志 `.local/maintenance.log` 最多 3 份、每份 1 MB。
- 手动与自动完整备份统一只保留本项目 `.local/backup/` 中最新一份受管有效包。新包及当前镜像离线包都校验成功后，旧受管包（含升级前发布回退点）移入 Windows 回收站；无归属标记、归属不匹配、损坏或失败材料保留供人工检查。Windows 需安装 `deploy/compact/requirements.txt` 中的回收站依赖；其他系统不回退为永久删除，而是停止轮换并要求人工处理。
- 当前镜像离线包仅保存在 `.local/current-runtime-backup/runtime-images.tar`。每天镜像未改变时只校验并复用；版本改变时，先验证新镜像包，再回收旧包。`retire_images.py` 不再导出旧镜像回滚 tar，只保留退役清单。恢复镜像执行 `python deploy/compact/backup_images.py restore`；单独刷新当前包执行 `python deploy/compact/backup_images.py refresh`，要求最近完整数据备份与当前容器镜像一致。
- 旧文件进入回收站后仍占宿主机空间，回收站也可能按容量淘汰旧项；不自动清空回收站。新包失败不处置上一份完整恢复材料。
- 备份包含私有账号和密钥，不提交 GitHub。本机备份不能抵御本机磁盘故障。媒体及既有历史备份本身仍会占空间，需要人工评估；日志上限不等于整个项目空间恒定。

## 本机监控

默认新增三个服务，全部只绑定 `127.0.0.1`：

| 服务 | 地址 | 保留策略 |
| --- | --- | --- |
| Prometheus | http://127.0.0.1:24590/ | 历史块保留目标为 7 天／256 MB；压缩 WAL 和当前数据另占少量空间，不是整个卷的硬配额 |
| Alertmanager | http://127.0.0.1:24591/ | 本机告警状态，48 小时保留 |
| Grafana | http://127.0.0.1:24592/ | 预置 Tianji Reliability 面板，用户 `tianji` |

Grafana 密码读取本机 `.env` 的 `ACCEPTANCE_GRAFANA_PASSWORD`；采集令牌仅保存在忽略目录，业务指标接口继续要求内部凭证。告警覆盖模块不可用、事件积压、失败持久任务、渠道核对异常和过去赛季阻塞。备份启用时另监测实际备份失败和超过 26 小时未成功完整备份；当前本机备份与对应告警已停用，面板应显示停用状态，不能用“无备份告警”判断已有恢复能力。

告警只在本机展示，没有邮件、Webhook 或其他外部通知。Docker 全部关闭时监控也关闭；重新运行后会反映启用中的监测项和未处理故障。健康检查并不会自动重启卡死的应用，需要查看告警和业务事实再处理。

## 失败发现与管理处理

可靠性页面按模块独立查询业务操作、事件投递和消费失败；身份模块 `auth` 同样可查。三类列表支持分页及精确标识查询，旧列表接口继续保留。业务操作可按 `RETRY_EXHAUSTED` 筛选，正常业务校验拒绝不触发基础设施故障告警。查询失败时只关闭对应区块；切换模块会清空旧记录，重放始终绑定记录来源模块。

关注 `tj_operations_retry_exhausted`、`tj_operations_oldest_seconds` 和 `tj_reliability_metrics_last_success_timestamp_seconds`。采集成功时间停滞时，旧零值不能证明健康；先检查该模块数据库连接和采集异常。重试耗尽时先核对请求、事件或业务事实及失败原因，再修复依赖并重放；版本冲突后重新查询，不能反复使用旧版本提交。重放只是重新安排处理，完成与否以刷新后的持久状态及业务结果为准。

告警仅投递本机 Alertmanager 面板，不宣称已接通外部通知。排障顺序为：确认模块与追踪编号 → 核对失败原因和已有业务结果 → 修复依赖 → 按原标识重放 → 确认状态、业务结果与告警恢复。

## 隐私申请的人工处理

现有“隐私权利申请”页面显示最多100条待处理记录。运营人员按申请编号核对申请人、请求类型、保留域、状态和版本，将受理中的申请更新为 `IN_PROGRESS`；并发处理发生409时重新查询，不覆盖另一名处理人的结果。

账户资料下载只包含账户资料与同意记录。完整导出须由各业务域的授权人员提取申请人本人的交易、学习、考试和安全资料，经核对后通过运营方已确定的私有渠道交付；申请记录只保存证据引用，不粘贴导出内容、密码、令牌或验证码。注销已禁用账户并清除公开资料，跨业务数据仍由运营按发布的保留规则审核，不能把 `retain_until` 当成已自动删除的证明。

完成前记录处理理由和实际交付／清理证据引用，再按当前版本提交 `COMPLETED`。证据未准备齐时保持处理中；拒绝请求使用 `REJECTED` 并记录依据。前端状态变更不会自动完成跨域导出或永久删除，详细接口和责任边界见[账户与隐私说明](account-security.md#隐私权利与责任边界)。
