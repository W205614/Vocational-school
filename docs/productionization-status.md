# 全链路改造与验收报告

基线：`c1b7df1`。分支：`codex/production-hardening`。日期：2026-10-06。

本次实现已在独立数据库和单机环境验收。原 `tianji-desktop` 的 20 个容器、数据卷、备份、凭据，以及用户原有未提交的 `.gitignore` 和 `deploy/docker` 材料未纳入改造提交。原容器入口仍运行旧版；本次没有生产切换。原 VMware `tjxt-init` 处于挂起状态且没有运行进程，Docker 使用的是另一个 WSL 2 环境。

## 并发测量

固定种子 20261006；每档有限竞争为 200 个请求、库存 100；持续窗口为每档 60 秒的闭环请求。并发为 1、10、50、100、200，延迟包括持久操作完成和客户端轮询，单位为秒；吞吐是已完成的业务操作数/秒。

测试访问独立营销服务，数据库池 8，合成用户 ID，只写验收库；没有覆盖网关、真实支付渠道和长时间运行。机器为 Ryzen 5 6600H（6 核/12 线程）、约 32 GB RAM、Windows、Docker Desktop，旧部署及另一个项目的容器同时存在。不能由本地一分钟窗口推断生产可持续 QPS。

“前”是已经完成正确性改造、批次 20 的中间检查点，不是原提交 `c1b7df1`。“后”是批次 100 的检查点。数据量、服务数和 JVM 产物运行方式也发生变化，因此差异是观察结果，不能全部归因于某一个参数。第一次后测期间还进行了应用户请求的虚拟机状态只读查询，保留为诊断数据。

200 并发的两个后测窗口观察到约 43～64 操作/秒、P99 约 4.7～9.3 秒，波动仍大；10 并发吞吐下降，50 并发的尾延迟也没有全面改善。以上证据支持并发正确性和部分高并发吞吐改善，不支持“所有负载全面提速”或生产容量承诺。

有限竞争各档均恰好 100 成功、100 库存不足等业务失败，意外错误为 0，发放记录和库存一致；持续窗口各档无超发、重复或意外错误。吞吐提高不能掩盖尾延迟；当并发提高到 200，排队与热点行竞争仍显著，应按实际业务延迟 SLO 限制接单量，不能继续无限加线程。

详细原始统计含 P95/P99、样本数、窗口内完成数/排空耗时、数据库锁等待、连接池、执行器、堆内存和事件积压指标，见 [脱敏证据目录](evidence/2026-10-06)。

## 发布与剩余边界

本地实现、功能回归和单机应用恢复已有证据。下列事项尚未完成，不能当作已上线能力：

- 原系统尚未切换。14 个非 root Linux 服务镜像已逐个检查启动、真实 readiness/OpenAPI、768 MiB 内存上限、日志目录与优雅退出；两端 Nginx 镜像已通过完整业务浏览器路径。逐个服务镜像的跨服务依赖及浏览器后台使用宿主机固定 JAR 和独立 Compose 基础设施，完整容器栈同时运行仍需专用资源窗口验证。
- Nacos 生产配置、真实支付宝/微信签名和证书、短信供应商、云存储/视频及多节点数据库/MQ/Redis/ES 高可用，需要独立环境和有效凭据实测。本地模拟标志在真实环境被拒绝，不自动回退模拟成功。
- 后台完整 CRUD 组合、任意自定义员工角色委派、长期容量/故障组合尚未全面验收。部分界面字段仍人工维护，生成类型不等于所有调用已静态校验。
- 云媒资保存路径仍包含数据库事务内的供应商调用；通知编辑版本仍沿用时间粒度。真实供应商投递是否收到、跨重试去重仍取决于其协议，不能把本地 Inbox 当作供应商恰好一次交付。
- 每周积分统计汇总已有积分流水；本次没有定义新的学习/笔记奖励政策，目前积分事件沿用签到与问答规则。

迁移脚本遇到重复数据或校验和变化会停止，不删除历史记录绕过约束；MySQL DDL 不可用事务整体回滚。切换前必须独立备份恢复演练、停旧写任务、清理/归档积压、重建历史权益和销量、核对业务关系，再执行流量切换。新版本写入后回退必须保留新增支付事实和业务事件，不能简单删表。具体步骤见 [运维与回退](reliability-runbook.md)，本地复现见 [验收 README](../deploy/acceptance/README.md)。

## 本机运行资源

验收结束后已停止本次临时 Java 服务、旧本地模拟器和验收基础容器，持久卷、备份、对象、镜像及脱敏证据保留。原 `tianji-desktop` 的 20 个容器继续健康运行；本次没有操作其他项目容器。停机核对见证据目录中的 `cleanup.json`。后续复验使用验收 README 恢复基础服务并启动相同隔离资源。
