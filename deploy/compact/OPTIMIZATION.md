# 性能工具协议与验证边界

当前交付没有完成当前源码的正式容量或 Java RSS 对照验收。200 并发容量、查询／命令延迟门槛以及合并部署降低 20% Java RSS 均为待验证目标；源码、启动检查、功能测试或 GitHub CI 通过不能替代实际测量。

## 工具职责

| 工具 | 作用 |
| --- | --- |
| `mixed_fixture.py`、`load_workflows.py` | 独立合成夹具与查询、笔记、进度、考试、交易和领券工作流 |
| `mixed_load.py`、`load_telemetry.py` | 冻结负载、执行测量并记录延迟、业务事实与资源指标 |
| `run_baseline.py`、`run_post_measurements.py` | 串行编排修复前后独立／合并部署的对照测量 |
| `perf_protocol.py` | 维护调度、工作负载覆盖、延迟、样本和 RSS 判定契约 |
| `performance_acceptance.py` | 校验四组原始报告的提交、快照、镜像、负载和哈希绑定 |
| `release_gate.py` | 完整交付模式要求正式性能证据；functional 模式明确将性能标为延期 |

## 正式协议

`perf-3h-v1` 对每种配置执行 10／50／100 并发各 300 秒一轮，再执行 200 并发各 600 秒三轮，共六轮、45 分钟。修复前独立、修复前合并、修复后独立、修复后合并合计 180 分钟正式采样；初始化、恢复、预热、诊断和失败重测另计。`perf-long-v1` 为另一套较长调度，不能替代完整交付门禁要求的协议。

总并发包含全部业务用户。工作流比例为查询／笔记／进度／考试／交易／领券 50／10／15／10／10／5，具体随机种子、思考时间和工具字节指纹由生成报告绑定。各配置使用相同业务源码、基础快照、合法夹具和基础设施镜像，每轮恢复基线。只在明确归属的隔离部署执行，避免与日常业务、浏览器验收、构建、恢复或镜像下载重叠。

200 并发检查要求每个必需查询和命令有足够样本，查询 P95 不超过 500ms、命令 P95 不超过 3000ms，并核对完整工作流与业务不变量。非预期拒绝、429、5xx、超时、预热错误、采样不足及背景干扰都会导致失败。RSS 取全部业务 Java 与网关的稳定采样，再比较三个 200 并发轮次的中位数；合并部署相对同阶段独立部署降低至少 20% 才满足目标。

报告必须保留真实失败，不能删改样本、补写通过标记、混用旧批次或仅凭短时诊断宣称验收。对照双方及四组原始报告的源码、镜像、快照、负载与发布批次均需满足工具校验；参数或测量实现变化后重新生成相应证据。

`load_fixture.py`／`load_test.py` 的旧查询与笔记负载只用于局部链路诊断。任何本机合成数据测量都不能直接推断真实用户规模、长期稳定性、供应商能力或多节点高可用。

`mixed_load.py --protocol smoke` 沿用同一合成混合工作流，适合短时验证链路，仍要求独立 `tianji-opt-*` 环境、快照与源码／镜像绑定。通过条件包括测量完整、所有工作流至少成功一次、没有非预期请求或预热错误、队列已收敛、业务不变量通过且环境及遥测有效；不能因错误计数为空就把零完成工作流判为成功。smoke 不应用正式协议的样本数、延迟和 RSS 门槛，也不产生容量通过结论；现有混合负载未覆盖真实视频字节吞吐。
